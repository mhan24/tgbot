# 代码结构与维护

核对日期：2026-11-04。项目只依赖 Python 标准库，不需要 pip 安装第三方库。

## 模块职责

| 模块 | 职责 |
|---|---|
| `bot.py` | Telegram HTTP API、长轮询、主数据库、默认群过滤、验证、帮助、管理操作服务、消息删除队列、群主配置 |
| `moderation.py` | `/manage` 面板、黑白名单选择、按钮身份校验、拉黑确认、关闭与面板失效 |
| `jev_ads.py` | `/report`、后台 Jev 分类、群员投票、管理员驳回、确认后删广告并调用统一警告服务 |
| `appeals.py` | 私聊解封申请、群主审批、通知重试、统一解封调用 |
| `invitations.py` | 私聊专属邀请链接、入群申请归属与奖励接入 |
| `points.py` | 积分事件、北京时间每日额度、十连签到与保底、出金榜（由十连结果计算）、发言积分、统计与排名 |
| `milestones.py` | 积分门槛达标序号、第 N 位达标祝贺、通知补发 |
| `attention.py` | 完整三日只签到窗口、运行缺口保护、异常签到禁言 |
| `exchange.py` | 公开汇率接口、小时缓存、Decimal 交叉换算和数据更新时间 |
| `members.py` | 已观察用户名与 ID 索引，操作前重新核验用户名 |
| `binlookup.py` | BIN 请求、缓存、错误和限流处理 |
| `scripts/command_descriptions.json` | Telegram 英文命令及中文说明 |
| `scripts/update_commands.py` | 更新已有菜单说明、移除不在命令表的条目 |
| `tests/` | 使用模拟 Telegram/API 和内存 SQLite 的回归测试 |

## 更新处理

```text
Telegram getUpdates
  → 控制层：默认群设置
  → 只接受默认群和用户私聊的更新
  → 机器人：保存可用上下文、处理命令/验证/按钮
  → 主循环：后台 Jev、验证到期、通知及删除队列
  → 保存处理位置，继续长轮询
```

群消息仅接受默认群 ID。管理、Jev、出金榜、积分榜和解封等按钮保留群 ID 校验和权限校验，私聊入口直接针对默认群。

`Bot.call()` 统一发送 API 请求；群内普通 `sendMessage` 自动进入删除队列，交互消息通过 `keep=True` 暂缓普通清理。群内验证、审批、投票和管理面板各自负责在结束时安排清理。私聊只允许登记过的机器人旧步骤进入清理队列；最终预览和结果保留。完整生命周期见 [消息保留规范](MESSAGE_RETENTION.md)。

## 数据隔离

默认群使用 `/var/lib/tgbot/bot.sqlite3`；不再创建或加载其他群数据库。

| 数据类别 | 主要记录 |
|---|---|
| 控制层 | 群登记、启用状态、当前管理群和轮询位置 |
| 成员管理 | 验证、警告、违规事件、黑白名单、操作审计、面板与解封申请 |
| 积分活动 | 用户积分、积分事件、活动日、运行缺口、升级、首次达标、签到保底与十连结果 |
| 举报 | Jev 分类任务、案例状态、投票及卡片 |
| 清理 | 待删群消息、验证卡片、重试次数与到期时间 |

SQLite 数据和 `.env` 不放入 Git。数据库采用 WAL；备份应使用 SQLite backup API 或停服后完整复制，避免只复制正在写入的主文件。

## 状态与重试

- 警告用稳定事件 ID 去重；第三次处罚另记录 `punished`，通知失败重试不重复封禁。
- 解封先成功调用 Telegram，再清理本地状态；失败不丢失黑名单。
- 管理面板绑定群、打开它的管理员、消息与有效期；操作后旧按钮失效，警告使用面板 token 作为事件的一部分。
- Jev 分类与投票持久保存；相同源消息最多警告一次。接口失败不触发处罚。
- 达标序号与补发状态持久保存；标签修改和祝贺通知分别处理。
- 十连签到在同一事务内保存保底计数、结果和积分；结果与保底播报分别记录发送标记，更新重试不重复发分，播报失败只补播报。
- 消息删除和通知采用有限重试；重启继续处理已保存的任务。

外部 API 和 SQLite 不能构成统一事务。因此仍需审计错误、保留失败状态并依赖事件去重，不能宣称所有外部调用严格只执行一次。

## 维护要求

开发约束统一维护于 [AGENTS.md](../AGENTS.md)，涵盖范围、交互、群隔离、权限、持久化、验证和部署；消息时长及接入规范见 [MESSAGE_RETENTION.md](MESSAGE_RETENTION.md)。修改功能前阅读对应规则，避免在多份文档中维护重复或冲突的约束。

测试命令、服务维护和恢复方法见 [DEPLOYMENT.md](DEPLOYMENT.md)。

`points.py` 的 `checkin_pity` 保存每人跨天四星/五星保底计数，`checkin_draws` 以签到事件保存十连结果、总分及结果/播报发送标记；签到积分、结果和保底更新在同一事务提交。`/milestones` 出金榜同样由 `checkin_draws` 的十连结果即时计算（按首次出金时间排序、不设门槛和人数上限），不维护独立榜单表，也无迁移步骤；`point_milestones` 仅保留积分门槛达标的“第 N 位达标”祝贺。

`retention.py` 区分短成功提示和失败/处罚通知，普通群回复遵循本群默认时长，失败通知通常为 120 秒；keep 和显式时长优先。private_steps 只登记机器人发出的配置、解封填写提示，下一步/结束时转入私聊 30 秒删除任务；预览与结果不登记。

## 失败恢复与重复更新

- 私聊活动参数使用持久去重，与步骤推进同事务提交；发送下一步提示失败后重放输入不会跳过步骤。按钮同时核验当前面板消息，旧按钮不能取消新步骤。
- 维护任务分别捕获错误并冷却重试，单项失败不阻断其他任务。永久失效的入群申请结束验证；权限或网络失败保留状态。白名单恢复成功后才标记验证完成。
- Telegram 返回损坏响应按可重试接口错误处理；过期回调确认不阻断已经持久化的业务。网络超时仍可能意味着远端已执行，结果消息不承诺绝对一次投递。

这些改进不代表所有 HTTP 调用已异步化；现有同步外部查询仍受接口超时影响。

成员管理采用同一卡片更新：操作后旧令牌作废，新令牌绑定相同消息并重新计算五分钟有效期；更新失败时提示重新打开，失败令牌不再有效。常用操作与“更多”分层展示，拉黑仍需二次确认。

数据库初始化仅创建当前完整结构，不维护旧版 ALTER、下线功能迁移或五步表单转换分支。重启恢复队列属于现用业务机制，继续保留；积分和现用处罚、配置等持久数据不因清理而重置。

## 破坏性变更与不兼容承诺

当前版本只保证自身结构自洽，不承诺兼容旧版本留下的数据或交互：

- **设置项**：启动时校验 `group_settings`，键不在 `GROUP_SETTING_SPECS` 或值无法按当前规则解析的行会被直接删除并记日志；布尔设置只接受 `1/0/on/off`。旧功能遗留的键不会出现在 `/settings`，也不会被静默沿用。
- **回调数据**：只接受当前格式，例如 `rank:{群ID}:{用户}:{页}`、`gold:{群ID}:{用户}:{页}`、`appeal:approve|reject:{群ID}:{申请}`、`mod:{群ID}:{令牌}:{动作}`、`gs:{动作}:{群ID}:{用户}:{键}`。旧格式按钮返回“无效/已失效”，不再执行业务。
- **命令入口**：公开入口只有 `/manage`、`/audit`、`/status`。旧管理命令（`/warn`、`/mute`、`/ban`、`/white` 等）没有解析分支，`/manage` 面板通过 `Bot.moderate()` 动作服务执行。
- **消息时长**：不按文案关键词猜类别，失败/警告/处罚通知显式使用 `Bot.notice_seconds()`。
- **积分接口**：`Points.award()` 只处理发言积分，签到必须走 `Points.checkin()`。
- **外部响应**：汇率接口缺少数值型 `timestamp` 即视为无效，不使用文档中的 `date` 字段兜底。

以上变更是有意的：代码不转发旧格式、不写兼容分支，旧库与旧按钮需要现场清理或重新打开入口。
